# Decide

Не генератор «единственно правильного решения» и не генератор ADR. Роль: найти решение, которое сейчас действительно блокирует движение, при необходимости исследовать его, и предложить лучший вариант — одну рекомендуемую стратегию, а не абсолютную истину.

```
вопрос → (исследование, если нужно) → рекомендация → выбор человека → запись
```

`/decide <вопрос>` — новое решение. `/decide PDEC-NNN` — вернуться к открытой карточке или зафиксировать выбор.

## Правила

- **Решение принимает человек.** Агент может `PROPOSE`, но не может сам считать решение принятым — никогда не ставить `ACCEPTED` самостоятельно. Карточка живёт как `PROPOSED`, пока пользователь не выбрал. Это касается всех решений о технологиях и архитектуре без исключений — `/decide` не принимает их за человека.
- Выбор против рекомендации записывается как выбранный, без повторных аргументов.
- **Не создавать decision ради decision.** Карточка нужна, только если решение: меняет архитектуру, ИЛИ влияет на важное поведение, ИЛИ трудно/дорого отменить позже, ИЛИ имеет реальный trade-off между вариантами (полный критерий и примеры — `rules/core/project-state.md`'s Decisions). Иначе это деталь реализации — реши её по ходу работы, без карточки.
- Всегда давать одну рекомендацию. «Зависит от обстоятельств» — не ответ.
- **Alternatives — только реальные.** Показывать 1-2 наиболее релевантные, только если у них есть содержательный trade-off с рекомендацией. Не изобретать альтернативы для вида; если очевидный вариант один — секцию не показывать.
- **Матрица только при настоящем trade-off** — когда варианты действительно равноценны и выбор неочевиден. Для тривиальных решений — никакой таблицы.
- В матрице только те критерии, которые реально важны для этого решения — обычно 3-4 из: complexity, time, risk, cost, scalability, reliability, maintainability, reversibility. Не выводить все подряд.
- Максимум 2-4 варианта. Заведомо нежизнеспособные не показывать.
- Карточка короткая по контракту: вопрос, рекомендация, 2-3 «почему», альтернативы (если есть), один trade-off, статус. Ни контекста, ни хода рассуждений.
- Пишет только `.ai/decisions.md` (карточка) и строку индекса в `Decisions` в `.ai/project.md`. Код и task-файлы не трогает. Внутритасковое решение — это `DEC-NNN` в самом task-файле (`rules/core/task-context.md`), не сюда.
- Persist-before-report: записать, перечитать, только потом показывать. Реконсиляция перед записью (`rules/core/common-rules.md`).
- Решение, отменяющее прежнее, не редактирует его задним числом: старая карточка получает `SUPERSEDED by PDEC-NNN`, новая пишется рядом.
- **Context-aware, не context-dump.** Читать репозиторий или `docs/` только если это меняет рекомендацию — и только тот файл, который отвечает на конкретный вопрос (`rules/core/common-rules.md`'s Source of truth). Никогда не загружать весь `docs/` целиком; если ответ уже есть в `project.md` или `Comprehension Tips` задачи — не перечитывать источник заново.

## Формат карточки

`.ai/decisions.md`, per `rules/core/project-state.md`:

```
## PDEC-NNN
Question: <что решаем>
Recommendation: <вариант>
Why:
- <причина>
- <причина>
Alternatives: <опустить, если нет реальных>
- <вариант> — <одна строка, почему нет>
Trade-off: <одна строка — цена самой рекомендации>
Status: PROPOSED | ACCEPTED | SUPERSEDED by PDEC-NNN
```

`PDEC-NNN` — следующий по порядку, id не переиспользуются.

## Вывод (на русском)

Реальные альтернативы, без матрицы — обычный случай:

```
PDEC-004

Question:
Как хранить тикеты?

Recommendation:
PostgreSQL

Why:
- структурированные данные;
- нужны фильтрация и поиск;
- предсказуемая консистентность;
- достаточно для MVP.

Alternatives:
- SQLite — проще локально, но хуже отражает продакшн-архитектуру;
- in-memory — совсем просто, но данные теряются и запросы ограничены.

Trade-off:
Немного больше локальной настройки, чем у альтернатив.

Status:
PROPOSED

Берём PostgreSQL?
```

Один явно лучший вариант — без Alternatives:

```
PDEC-006

Question:
Чем хранить сессии?

Recommendation:
Тот же PostgreSQL, что уже в стеке

Why:
- уже используется;
- отдельный сервис не нужен при такой нагрузке.

Trade-off:
Хуже подходит для очень большого ephemeral state — не наш случай.

Status:
PROPOSED
```

Настоящий trade-off между равноценными вариантами — тогда матрица:

```
PDEC-005

Question:
Как доставлять обновления в UI?

| Вариант | Сложность | Время | Риск | Масштаб |
|---|---|---|---|---|
| Polling | низкая | быстро | низкий | средний |
| SSE | средняя | средне | средний | высокий |
| WebSocket | высокая | долго | высокий | высокий |

Recommendation:
SSE

Why:
- обновления только в одну сторону;
- дешевле WebSocket в эксплуатации;
- polling не тянет нужную частоту.

Alternatives:
- Polling — проще всего, но не тянет частоту обновлений;
- WebSocket — избыточен для одностороннего потока.

Trade-off:
Сложнее polling, нужен прокси, который держит соединение.

Status:
PROPOSED

SSE / Polling / WebSocket?
```

После выбора — одна строка, без пересказа:

```
PDEC-005 → SSE. ACCEPTED.
```
