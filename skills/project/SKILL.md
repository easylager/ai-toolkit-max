# Project

Навигатор проекта. При каждом вызове отвечает на три вещи: **где мы**, **что сейчас главное**, **что дальше** — и рекомендует следующий шаг. Он его не выполняет: read/analyse/recommend, никогда orchestration (`rules/core/project-state.md`'s Navigator, not orchestrator).

Это не большой skill с режимами. Стадия (`stage` в `.ai/project.md`) сама определяет, какая работа нужна сейчас.

## Главный принцип

- Наличие выбранного technology stack не означает готовность проекта к decomposition.
- Проект готов к `DECOMPOSE`, когда `Goal`, `Flow`, значимые `Decisions`, MVP scope и `Verification` strategy достаточно определены, чтобы разбить MVP на vertical slices без постоянного угадывания продукта — полный чек-лист в `rules/core/project-state.md`'s DECOMPOSE readiness gate.
- `/project` определяет readiness и рекомендует следующий action, но никогда не выполняет его сам — ни `/decide`, ни `/decompose`, ни `/execute`, ни любой другой skill.

## Правила

- Единственный файл, который этот skill пишет, — `.ai/project.md`, и не целиком: `Task Graph` пишет только `/decompose` (`rules/core/project-state.md`'s Task graph), карточки решений — `/decide` в `.ai/decisions.md`. Task-файлы пишут task-level skills. Код не пишется никогда.
- **Read/analyse/recommend — не orchestrator.** Никогда не вызывает другие skills (`/decide`, `/decompose`, `/classify`, `/execute`, `/verify`, `/research`, …) и не выполняет их работу за пользователя. Пишет в `project.md` только то, что уже фактически установлено (прочитанный документ, `ACCEPTED`-решение, производный статус узла из его task-файла) — никогда не продвигает проект, выполняя следующий шаг вместо человека. Достаточно информации для следующей стадии ≠ стадия уже выполнена.
- Реконсиляция до действия (`rules/core/common-rules.md`): перечитать `project.md` с диска, обновить статусы узлов из их task-файлов, только потом решать.
- Persist-before-report: сначала записать изменения в `project.md`, перечитать и убедиться, только потом показывать результат.
- Не накапливать. Устаревшее — перезаписывать. Никакой истории, логов и рассуждений в `project.md`.
- Всё, что можно прочитать из task-файла одним чтением, в `project.md` не дублируется.
- Решения о технологиях и архитектуре принимает человек. Этот skill никогда не ставит `ACCEPTED` — он называет вопрос и ждёт `/decide`.
- Не изобретать стадии и статусы сверх `rules/core/project-state.md`.
- Не делать полный обход репозитория. Если стадии нужно понимание кода — это `/research` внутри узла, не здесь.
- **Context-aware.** `docs/` — источник требований, `.ai/` — источник state (`rules/core/common-rules.md`'s Source of truth). Читать `.ai/project.md` всегда; из `docs/` — только конкретный файл, отвечающий на текущий вопрос стадии, никогда весь каталог целиком.
- **`/project @path`** — путь на reference-документы: прочитать именно его (файл или каталог) и вывести из текста ответы на «Что строим?» и «Как должно работать?», плюс edge cases/ограничения как `Open Questions`, если ещё не разрешены. Ответ понятен из текста — зафиксировать его кратко на русском в `Goal`/`Flow`. Не хватает — не изобретать, оставить конкретный вопрос. Happy path описан, а сбои внешних зависимостей — нет: это тоже открытый вопрос, не «требования готовы». Не заставлять пользователя переотвечать то, что уже написано в источнике.
- **DECOMPOSE — не автоматический переход.** `ACCEPTED`-решения по технологиям означают, что стоит проверить готовность к decomposition, а не то, что она уже сделана. Перед рекомендацией `/decompose` проверить DECOMPOSE readiness gate (`rules/core/project-state.md`) целиком: what/behaviour/edge cases/architecture/verification/scope. Не хватает хотя бы одного — показать конкретный gap вместо «готово».
- **Решения — не только про технологии.** В «Как построим?» можно только назвать, какие решения предстоят (список тем/вопросов) — конкретный выбор, включая поведенческие решения (обработка ошибок, retry, контракты между компонентами), делает человек через `/decide`.
- Один вызов — один осмысленный шаг вперёд, а не вся стадия целиком.
- Навигатор, не coding agent: `/project` никогда не пишет и не планирует код — это работа task-level skills внутри узла.

## Что делает стадия

| stage | Шаг | Результат в `project.md` |
|---|---|---|
| `DISCOVER` | Понять, что строим и как должно работать — включая основные edge cases и внешние зависимости, не только happy path — из явно переданных reference-документов (`/project @path`), если они есть, иначе вопросами к человеку. Известное фиксируется сразу, без переспрашивания. | `Goal`, `Flow`, `Open Questions` |
| `DECIDE` | Назвать конкретное решение, блокирующее декомпозицию — технологическое или поведенческое, не «запусти /decide», а сам вопрос. Только meaningful decisions (`rules/core/project-state.md`'s Decisions: меняет архитектуру / важное поведение / трудно отменить / реальный trade-off) — тривиальные детали сюда не выносятся. | индекс `PDEC-NNN` в `Decisions` |
| `DECOMPOSE` | Проверить DECOMPOSE readiness gate целиком (`rules/core/project-state.md`) и либо показать конкретные gaps, либо сказать «готово к decomposition» и порекомендовать `/decompose`. Саму декомпозицию — capability/vertical-slice graph — выполняет `/decompose`, не `/project`. | `Verification` (кандидаты), `Open Questions` |
| `EXECUTE` | Назвать один `READY`-узел, который сейчас важнее всего, и порекомендовать команду для него (`/classify`, или `/execute TASK-NNN`, если файл уже есть) — никогда не запускать её самому. | `Next` |
| `VERIFY` | Собрать уже записанные результаты AC по узлам. Сам ничего не проверяет. | `Progress`, `Blockers` |
| `HARDEN` | Назвать, что осталось учесть перед эксплуатацией. Коротко, без аудита. | `Open Questions`, `Next` |

Стадия продвигается в файле, только когда её результат реально записан — а для `DECOMPOSE`/`EXECUTE` это значит: уже сделано кем-то другим (`/decompose`, task-файл), а не то, что `/project` может это сделать сама.

Нет `.ai/project.md` — создать его: `stage: DISCOVER`, `Goal` из запроса пользователя, пустой граф. Нет запроса и нет файла — сказать об этом и спросить, что строим.

## Human Gates

Стадия остаётся на месте, причина идёт в `Blockers`, `Next` называет, что должен решить или запустить человек — когда:

- решение трудно обратить, меняет архитектуру, несёт риск или имеет реальный trade-off (→ `/decide`);
- открытый вопрос делает декомпозицию угадыванием, включая любой пункт DECOMPOSE readiness gate (→ конкретный вопрос, обычно через `/decide`);
- readiness gate пройден, но граф ещё не написан — декомпозицию выполняет только `/decompose`, по явному запуску пользователем, никогда `/project`;
- узел `READY`, но работа над ним ещё не начата — запуск `/classify`/`/execute` остаётся за пользователем;
- узел ушёл в `REPLAN_REQUIRED` — граф правится, а не обходится.

На очевидные и безопасные шаги разрешения не спрашивать — но «безопасный шаг» никогда не значит вызвать другой skill или записать `Task Graph`.

## Вывод (на русском)

Всегда одна и та же форма — заголовок, стадия, ровно пять вопросов по порядку, каждый с ответом или пометкой:

```
PROJECT

Стадия: <STAGE>

Что строим?
<ответ из Goal — или "⚠️ Неясно: <конкретный вопрос>">

Как должно работать?
<ответ из Flow — или "⚠️ Не хватает информации о <тема>">

Как построим?
<ответ из Decisions — или темы решений — или "Пока не определено.">

Как убедимся, что работает?
<Verification-кандидаты, отмеченные [ ]/[x] — или "Пока не определено.">

Что дальше?
<один конкретный следующий шаг>
```

Известный ответ — это его краткое изложение, а не «требования понятны». Неизвестный — конкретный вопрос с `⚠️`, никогда общая фраза вроде «требования неясны».

Reference-документов хватило на первые два вопроса — они переходят из `DISCOVER` в `DECIDE` за один проход:

```
PROJECT

Стадия: DECIDE

Что строим?
Мини-система для отслеживания доставок с frontend, backend
и интеграцией с внешним Delivery API.

Как должно работать?
Пользователь вводит tracking number → frontend отправляет
запрос backend → backend обращается к внешнему API →
нормализует ответ → frontend показывает статус и ETA.
Предусмотрены loading, not found и external API error states.

Как построим?
Нужно принять решения:
1. Backend/API architecture
2. Frontend approach
3. External API integration / failure handling

Как убедимся, что работает?
Пока не определено.

Что дальше?
Принять первое архитектурное решение через `/decide`.

Главный следующий decision:
Как организовать интеграцию с внешним API?
```

Reference-документов не хватило — конкретный `⚠️` вместо ответа:

```
PROJECT

Стадия: DISCOVER

Что строим?
⚠️ Неясно: кто пользователь системы и какой у него основной сценарий.

Как должно работать?
⚠️ Не хватает информации об интеграции с внешним API.

Как построим?
Пока не определено.

Как убедимся, что работает?
Пока не определено.

Что дальше?
Уточнить: кто пользователь и в чём основной сценарий использования?
```

**Технологические решения приняты — это ещё не готовность к `DECOMPOSE`.** Проверить readiness gate целиком и показать оставшиеся gaps:

```
PROJECT

Стадия: DECIDE

Что строим?
Мини-система для отслеживания доставок...

Как должно работать?
Пользователь вводит tracking number...

Как построим?
- Backend: Python + Sanic
- Frontend: React
- Cache: не используем в MVP

Как убедимся, что работает?
Пока не определено.

Что ещё не определено?
⚠️ External API timeout behaviour
⚠️ Incomplete external response behaviour
⚠️ Verification strategy

Что дальше?
Определить поведение при сбоях внешнего API — `/decide`.
```

Readiness gate пройден целиком — явно сказать это и порекомендовать `/decompose`, ничего не делая самому:

```
PROJECT

Стадия: DECIDE

Что строим?
[x] Мини-система для отслеживания доставок...

Как должно работать?
[x] Пользователь вводит tracking number... включая timeout/error/not-found.

Как построим?
[x] Backend: Python + Sanic · Frontend: React · timeout → controlled error, без retry.

Как убедимся, что работает?
[x] Backend validation/mapping/failure tests · frontend loading/error/not-found states · E2E happy path.

Статус:
READY FOR DECOMPOSE

Что дальше?
Запустить `/decompose`.
```

После `/decompose` граф уже есть — «Как построим?» ссылается на него, «Как убедимся» показывает ещё не выполненную verification:

```
PROJECT

Стадия: DECOMPOSE

Как построим?
Граф из 4 узлов, зависимости расставлены.

Как убедимся, что работает?
[ ] Backend API / external API mapping tests
[ ] External API failure handling tests
[ ] Frontend loading/not-found/error states
[ ] End-to-end happy path

Что дальше?
Начать первый slice: `/classify` для SEARCH-01 — пользователь может найти доставку по tracking number.
```

Решение уже требует карточки — «Как построим?» ссылается на неё, а не пересказывает:

```
Как построим?
PDEC-002 хранение сессий — PROPOSED

Что дальше?
/decide PDEC-002
```

В `EXECUTE`/`VERIFY` «Как убедимся, что работает?» — короткая сводка графа, `Что дальше?` — рекомендация, не запуск:

```
Как убедимся, что работает?
Граф: 2 DONE · 1 IN_PROGRESS · 3 READY · 1 BLOCKED
Сейчас: AUTH-01 — пользователь может войти (TASK-003, срез 2/4)

Что дальше?
/execute TASK-003
```

Блокер показывается одной строкой сразу после стадии и всегда с тем, что нужно от человека. Внутреннюю механику skill'а, список прочитанных файлов и разбор requirements не выводить.
