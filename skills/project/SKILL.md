# Project

Навигатор проекта. При каждом вызове отвечает на три вещи: **где мы**, **что сейчас главное**, **что дальше** — и делает следующий шаг, если он очевиден и безопасен.

Это не большой skill с режимами. Стадия (`stage` в `.ai/project.md`) сама определяет, какая работа нужна сейчас.

## Правила

- Единственный файл, который этот skill пишет — `.ai/project.md` (`rules/core/project-state.md`). Карточки решений пишет `/decide` в `.ai/decisions.md`. Task-файлы пишут task-level skills. Код не пишется никогда.
- Реконсиляция до действия (`rules/core/common-rules.md`): перечитать `project.md` с диска, обновить статусы узлов из их task-файлов, только потом решать.
- Persist-before-report: сначала записать изменения в `project.md`, перечитать и убедиться, только потом показывать результат.
- Не накапливать. Устаревшее — перезаписывать. Никакой истории, логов и рассуждений в `project.md`.
- Всё, что можно прочитать из task-файла одним чтением, в `project.md` не дублируется.
- Решения о технологиях и архитектуре принимает человек. Этот skill никогда не ставит `ACCEPTED` — он вызывает `/decide` и ждёт выбора.
- Не изобретать стадии и статусы сверх `rules/core/project-state.md`.
- Не делать полный обход репозитория. Если стадии нужно понимание кода — это `/research` внутри узла, не здесь.
- **Context-aware.** `docs/` — источник требований, `.ai/` — источник state (`rules/core/common-rules.md`'s Source of truth). Читать `.ai/project.md` всегда; из `docs/` — только конкретный файл, отвечающий на текущий вопрос стадии, никогда весь каталог целиком.
- **`/project @path`** — путь на reference-документы: прочитать именно его (файл или каталог) и вывести из текста ответы на «Что строим?» и «Как должно работать?». Ответ понятен из текста — зафиксировать его кратко на русском в `Goal`/`Flow` и отметить вопрос отвеченным. Не хватает — не изобретать, оставить конкретный `Open Question`. Не заставлять пользователя переотвечать то, что уже написано в источнике.
- **Решения не принимаются здесь.** В «Как построим?» можно только назвать, какие решения предстоят (список тем/вопросов) — конкретную технологию выбирает `/decide`, а не `/project`.
- Один вызов — один осмысленный шаг вперёд, а не вся стадия целиком.
- Навигатор, не coding agent: `/project` никогда не пишет и не планирует код — это работа task-level skills внутри узла.

## Что делает стадия

| stage | Шаг | Результат в `project.md` |
|---|---|---|
| `DISCOVER` | Понять, что строим и как должно работать — из явно переданных reference-документов (`/project @path`), если они есть, иначе вопросами к человеку. Известное фиксируется сразу, без переспрашивания. | `Goal`, `Flow`, `Open Questions` |
| `DECIDE` | Назвать конкретное решение, блокирующее декомпозицию — не «запусти /decide», а сам вопрос. Только meaningful decisions (`rules/core/project-state.md`'s Decisions: меняет архитектуру / важное поведение / трудно отменить / реальный trade-off) — тривиальные детали сюда не выносятся. | индекс `PDEC-NNN` в `Decisions` |
| `DECOMPOSE` | Разбить на узлы-возможности (поведение, не файлы), проставить зависимости и `READY`/`BLOCKED`. | `Task Graph` |
| `EXECUTE` | Выбрать один `READY`-узел и передать его в task workflow (`/classify` → … → `/verify`). | `status` узла, `task` узла, `Next` |
| `VERIFY` | Собрать уже записанные результаты AC по узлам. Сам ничего не проверяет. | `Progress`, `Blockers` |
| `HARDEN` | Назвать, что осталось учесть перед эксплуатацией. Коротко, без аудита. | `Open Questions`, `Next` |

Стадия продвигается, только когда её результат реально записан в файл.

Нет `.ai/project.md` — создать его: `stage: DISCOVER`, `Goal` из запроса пользователя, пустой граф. Нет запроса и нет файла — сказать об этом и спросить, что строим.

## Human Gates

Стадия остаётся на месте, причина идёт в `Blockers`, `Next` называет, что должен решить человек — когда:

- решение трудно обратить, меняет архитектуру, несёт риск или имеет реальный trade-off (→ `/decide`);
- открытый вопрос делает декомпозицию угадыванием;
- узел ушёл в `REPLAN_REQUIRED` — граф правится, а не обходится.

На очевидные и безопасные шаги разрешения не спрашивать.

## Вывод (на русском)

Всегда одна и та же форма — заголовок, стадия, ровно пять вопросов по порядку, каждый с ответом или пометкой:

```
PROJECT

Стадия: <STAGE>

Что строим?
<ответ из Goal — или "⚠️ Неясно: <конкретный вопрос>">

Как должно работать?
<ответ из Flow — или "⚠️ Не хватает информации о <тема>">

Как построим?
<темы решений / индекс PDEC-NNN — или "Пока не определено.">

Как убедимся, что работает?
<сводка графа/прогресса — или "Пока не определено.">

Что дальше?
<один конкретный следующий шаг>
```

Известный ответ — это его краткое изложение, а не «требования понятны». Неизвестный — конкретный вопрос с `⚠️`, никогда общая фраза вроде «требования неясны».

Reference-документов хватило на первые два вопроса — они переходят из `DISCOVER` в `DECIDE` за один проход:

```
PROJECT

Стадия: DECIDE

Что строим?
Мини-система для отслеживания доставок с frontend, backend
и интеграцией с внешним Delivery API.

Как должно работать?
Пользователь вводит tracking number → frontend отправляет
запрос backend → backend обращается к внешнему API →
нормализует ответ → frontend показывает статус и ETA.
Предусмотрены loading, not found и external API error states.

Как построим?
Нужно принять решения:
1. Backend/API architecture
2. Frontend approach
3. External API integration / failure handling

Как убедимся, что работает?
Пока не определено.

Что дальше?
Принять первое архитектурное решение через `/decide`.

Главный следующий decision:
Как организовать интеграцию с внешним API?
```

Reference-документов не хватило — конкретный `⚠️` вместо ответа, `Что дальше?` называет, что уточнить:

```
PROJECT

Стадия: DISCOVER

Что строим?
⚠️ Неясно: кто пользователь системы и какой у него основной сценарий.

Как должно работать?
⚠️ Не хватает информации об интеграции с внешним API.

Как построим?
Пока не определено.

Как убедимся, что работает?
Пока не определено.

Что дальше?
Уточнить: кто пользователь и в чём основной сценарий использования?
```

Решение уже требует карточки — «Как построим?» ссылается на неё, а не пересказывает:

```
Как построим?
PDEC-002 хранение сессий — PROPOSED

Что дальше?
/decide PDEC-002
```

В `EXECUTE`/`VERIFY` «Как убедимся, что работает?» — короткая сводка графа:

```
Как убедимся, что работает?
Граф: 2 DONE · 1 IN_PROGRESS · 3 READY · 1 BLOCKED
Сейчас: AUTH-01 — пользователь может войти (TASK-003, срез 2/4)

Что дальше?
/execute TASK-003
```

Блокер показывается одной строкой сразу после стадии и всегда с тем, что нужно от человека. Внутреннюю механику skill'а, список прочитанных файлов и разбор requirements не выводить.
